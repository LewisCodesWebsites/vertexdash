# VertexDash behaviour specification

This file is the only source of truth for the builder. Every entry describes WHAT the
original game does, never HOW its code does it.

## Rules for entries

- No code, pseudocode, assembly, symbol names or addresses from the original game.
- Values are measured behaviour: numbers, units, timings, shapes, formats.
- Every entry has an ID, a value, how it was measured, and a confidence level.
- Confidence: `measured` (observed directly), `derived` (calculated from measurements),
  `community` (from public community documentation, with link), `unverified`.

Entry format:

| ID | Behaviour | Value | Measured how | Confidence |
|----|-----------|-------|--------------|------------|

## 2. Cube mode

| ID | Behaviour | Value | Measured how | Confidence |
|----|-----------|-------|--------------|------------|
| CUBE-01 | Horizontal speed at each speed setting | Normal (default) speed: 1.29825 units per tick = 311.58 units/s. It stays constant on the ground, in the air, while landing, while standing on blocks and while a block side overlaps the outer box. The other speed settings (0.5×, 2×, 3×, 4×) are not measured yet. | Position readout every tick over three levels (more than 1,000 ticks in total). The x step was 1.29825 on every tick. | CUBE-02 | Gravity | While airborne, upward velocity drops by 0.0486 units/tick on every tick (2799.36 units/s²). Each tick the velocity changes first and then the position moves by the new velocity. So when the cube walks off a ledge from rest, its first airborne tick moves y by −0.0486, the second by −0.0972, and so on. No terminal velocity was reached in falls of up to 0.43 s (the fastest observed fall was about 2.44 units/tick). | Per-tick y readout through two full jumps and one ledge fall. The second difference of y was −0.0486 on every tick (spread ±0.00002 from 2-decimal display rounding). | measured |
| CUBE-03 | Jump initial velocity | 2.5155 units/tick upward (603.72 units/s). On the automatic re-jump while held (CUBE-05), the first tick moves the full +2.5155, then +2.4669, +2.4183, … | Per-tick y and velocity readout (Eclipse label) on 5 jumps. Fresh press: first change +2.46690. Held re-jump: first change +2.51550, next +2.46691. | measured |
| CUBE-04 | Jump height and duration | Fresh press on flat ground: the apex is 63.84691 units above the start (y 105 → 168.84691), reached on the 51st tick after the press. On the landing tick y is set exactly onto the surface and the vertical velocity becomes 0 (for example, y went from 106.28520 to 105.00000 rather than continuing to 103.82). Held re-jump: lands 105 ticks after the previous landing tick, with apex 66.36241 above the surface. | Full per-tick log of a jump in VDJump (tap at tick 8): apex at tick 59, landing at tick 111. | CUBE-05 | Jump buffering and hold-to-jump behaviour | A press while on the ground (or on a block top) starts a jump on the next tick, even if the input is released before that tick. Releasing early does not shorten a jump (there is no variable jump height). A press and release made entirely while airborne is not buffered: taps 5 ticks and 1 tick before landing both produced no jump. Not measured: a press started in the air and still held at landing. | Frame-stepped runs in VDJump: one with the mouse held through a landing, one released mid-air, and one with single taps at 5 ticks and at 1 tick before landing. The inner box is used for deaths from solids (OBJ-03). | Eclipse Show Hitboxes, measured on full-resolution captures at 112 px = 30 units (calibrated on a block). Outer box 112 px. Inner box 34 px = 9.1 ± 0.3 units. Bounds from death ticks: inner half-width between 4.28 and 5.58, outer half-width consistent with 15 (OBJ-01, OBJ-03). | measured |

## 3. Objects and collision

| ID | Behaviour | Value | Measured how | Confidence |
|----|-----------|-------|--------------|------------|
| OBJ-01 | Block hitbox and landing rules | Basic block (object id 1): solid box of 30 × 30 units centred on the object. Landing: on the tick a falling cube would move below the block's top while its outer box overlaps the block horizontally, y is set to top + 15 and vertical velocity to 0 (block top 120 → y 135). This works the same as landing on the ground. Standing: the cube stays supported while its outer box overlaps the block horizontally, and starts falling on the first tick where its left edge (x − 15) is past the block's right edge. It was supported at x − 15 = 388.755 and falling at x − 15 = 390.054, with the edge at 390. Sides: the outer box can overlap a block's side with no effect (no push-back and no speed change). The cube dies when its inner box reaches the block (see OBJ-03). Not measured: hitting a block from below, and exact-equality ties at edges. | VDBlock, frame-stepped. Run 1 had no input: the outer box overlapped the block's left face from x = 345.33 with no effect, and the cube died at x = 355.720 (inner edge 360.22 > 360; alive at 354.422, inner edge 358.92). Run 2 had a jump: landed on top at the predicted tick, rolled off at the edge as above, and landed on the ground at the predicted tick. | measured |
| OBJ-02 | Spike hitbox | Spike (object id 8, upright, default size): hazard box 6 wide × 12 tall, centred on the object's centre. For a spike resting on the ground (world y 105), the box spans world y 99–111 and x 552–558 for x = 555. The spike's triangular sprite is not used for collision. Other spike types and rotations are not measured yet. | Eclipse Show Hitboxes, full-resolution capture: hazard box 22 × 45 px (112 px = 30 units), giving 5.9 × 12.1 units, centred on the sprite. The death tick bounds the half-width to between 2.52 and 3.82 (OBJ-03). | measured |
| OBJ-03 | Death conditions | The cube dies on the same tick that either of these first becomes true: (a) its outer box (30 × 30) overlaps a hazard box (spike), or (b) its inner box (9 × 9) overlaps a solid block's box. Standing on, landing on or rolling off a block, and touching the ground, never kill. After a death the level restarts from tick 0 with a new attempt. Restart delay in normal play: not measured (the measurement mod's respawn-delay setting was active). | Death flag (Eclipse label) read every tick. VDSpike: alive at x = 536.177 (outer right edge 551.18), dead at x = 537.476 (552.48 > 552). VDBlock: inner-box rule as in OBJ-01. In both cases the position on the death tick had already advanced by one normal step. | measured; unverified (restart delay) |

## 4. Level format

| ID | Behaviour | Value | Measured how | Confidence |
|----|-----------|-------|--------------|------------|
| LVL-01 | Where your own levels are stored on disk | Windows (Steam): `%LOCALAPPDATA%\GeometryDash\CCLocalLevels.dat` holds the player's own (created) levels. `CCLocalLevels2.dat` sits next to it; what it is for is not determined. Other platforms are not measured. VertexDash should only ever read these files, never write them. | Created three levels in the editor and found them in this file after saving; before that, the file contained no levels. | measured; unverified (`CCLocalLevels2.dat`, other platforms) |
| LVL-02 | Level string encoding and compression | File: XOR every byte with 11 (0x0B), then URL-safe base64 decode (padding may be missing), then gzip decompress. The result is an XML plist (`gjver="2.0"`) of nested dictionaries. Inside the root `<dict>`, the plist uses abbreviated element names: `<d>` = dictionary, `<k>` = key, `<s>` = string, `<i>` = integer, `<r>` = real, `<t />` = true. A parser must accept both `dict` (root) and `d` (nested). Each level is a dictionary where key `k2` is the level name (a string, which may contain leading spaces: one level is stored as " VDBlock") and `k4` is the level string. The level string is itself URL-safe base64 + gzip. Decoded, it is plain text: sections separated by `;`, where the first section is the level header (level settings and colours, starting with `kS38`) and every later non-empty section is one object. | Decoded a copy of the save file by hand and found the three test levels with exactly the objects placed in the editor. This is the same scheme the community docs give for the main save file ([gamesave](https://wyliemaster.github.io/gddocs/#/resources/client/gamesave)) and the object string ([level string](https://wyliemaster.github.io/gddocs/#/resources/client/level-components/level-string)). | measured + community |
| LVL-03 | Object record fields used by Milestone 1 | Each object is a flat comma-separated list of key,value pairs. Keys used by M1: `1` = object id (integer; 1 = basic block, 8 = spike), `2` = x and `3` = y (floats, in units, object centre; see SIM-02 for the mapping to world coordinates; grid-aligned objects sit at 15 + 30k), `21` = main colour channel (integer, optional; seen once as 1004). `155` appears on every object, always 1 in the test levels, and has no known effect in M1, so ignore it. Unknown keys must be ignored. Example from VDSpike: `1,8,2,555,3,15,155,1`. | Decoded the three test levels (LVL-02) and compared them with what was placed in the editor and with the measured hitbox positions (OBJ-01, OBJ-02). Key meanings agree with the community [level string](https://wyliemaster.github.io/gddocs/#/resources/client/level-components/level-string) docs, which describe 155 as "suspected to be something related to optimizing colors". | measured + community |
